# Bellback runtimecandidate5: captured lethal pose, source-only WIP

This is runtime candidate 5 of the existing Bellback V6 Frame2 mesh, not a new art
version or likeness assessment. No runtime, contact, visual or collider acceptance
is claimed. Product build, browser combat and publication require coordinator GO
following the independent engine review. Candidate4 and its failed contact evidence
remain unchanged; no current public host is replaced by these sources.

## Exact input contract

The only metadata change from pinned arena-candidate4/metadata.json is
bodies[0].dims.rigidCorpse.posePolicy = "captured". The original eight meshes, eight
bones, 13,374 packed vertices, 435 exact hull vertices, unit rigid skin weights,
38,768 compressed payload bytes, living dimensions and bone transforms remain
identical. Candidate4's canonical support proof remains applicable because its
geometry and hull recipe are identical. That proof does not establish contact.

The isolated generator retains the original Tucked clips (including their unused
numeric death track), AI decision, attacks, timings, loot, held weapon, source
budgets and neutral-gray-v2 lighting. Only the preview source name changes outside
metadata. Captured policy intends to hold the exact lethal local pose while the
normal root throw begins immediately and the body tumbles. The runtime must skip
an authored death fold under this opt-in. This is one rigid body, not an articulated
ragdoll: the held silhouette and final settle may look stiff or awkward. Those are
explicit visual-review risks, not hidden quality claims.

The candidate admission pins every candidate4 source-freeze file and the manifest
itself. An updated receipt cannot authorize different native data, payload,
living dimensions, clips, AI, combat, prior metadata or hull support. Candidate5
has separate metadata/admission, generator, build entry, Vite config and tests.
Its manifest freezes all candidate-local editable sources and inherited inputs.
The independently reviewed shared engine/runtime closure is a separate coordinator
checkpoint; this local manifest is not a claim to freeze the entire app runtime.

## Prepared verification

- Node admission tests cover the exact delta, missing/wrong/null policy, rig,
  living dimensions, hull inflation, axis changes, root lift, callback, padding,
  payload location, stale hashes, mutable-receipt canonical tampering, tuple shape
  and false acceptance claims.
- Focused Vitest cases load the real packed native data through ordinary admission,
  verify deep copying and exact recipe delta, and compare source and emitted combat
  catalogue to candidate4.
- verify-source.mjs is read-only and checks exact source-freeze membership, byte
  counts, digests and strict candidate admission. It never builds or regenerates.
- No browser or product result is implied by source preparation. After GO, flat
  full combat and independent walk regression must run on the exact built host.

## Real orientation and terrain assessment, without implementation

Varied flat-ground kill orientations are achievable in this unchanged preview
through real movement, circling and sword impacts during normal combat. Record
actual lethal local poses, root quaternions, fixed/post and render contact through
the tumble and settled interval; do not force pose, health, velocity or body
transforms. Distinct attempts must demonstrate genuinely different measured
orientations rather than relabeling identical deterministic resets.

Terrain is not currently data-configurable in this preview host. TrainingArena's
makeRoom fixes the floor at Y=900 with fixed walls and a flat floor descriptor.
startPracticeDemo binds the player to a constant 900 height. PracticeCreature binds
its decision groundHeightAt, Animal heightAt/floorBelow/groundHeight and ThinkCtx
heightAt to the spawn height. Adding terrain fields to the candidate shard alone
would therefore not establish genuine terrain traversal or equivalent contact.

Existing shardfile authoring has an admitted terrain path (format/terrain,
format/shardSchema, game/shardfile/clientGround and clientRings) with real baked
collider payloads and matching height queries. A later separate terrain experiment
can use that established world host and unchanged admitted Bellback sources, or a
reviewed reusable data-driven practice terrain extension that supplies matching
render geometry, physics colliders and player/animal/decision queries. Either
changes the host/product closure and needs explicit review before its results can
be attributed to a preview. Merely adding obstacles in a browser, monkeypatching
height queries, rotating the floor after load or injecting physics is not an
acceptable terrain proof. No terrain implementation was made in candidate5.
