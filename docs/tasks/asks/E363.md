## API gaps (shard 5 build)

- **The generated lint files sit in a shared working tree.** `pnpm gen` in the shared checkout fails (another agent's
  uncommitted `src/kit/weapons/melee/SweptMelee.ts` imports `weaponActionGate`, which the working `#engine` doesn't
  export), and `lint/shard-words.generated.json` there already carries far-reach's words. So the shard is built,
  typechecked and tested on a clean export of HEAD, and its `shard-words` entry is committed through a private index
  (HEAD + this slug only). Wanted: `gen-shards` able to write one slug's entry, or the file split per slug.
- **No flying creature in the API.** `SpeciesRow` / `ThinkCtx` are ground creatures: `ctx.steer` avoids slopes and
  the ground follow owns `y`. The ray flies through `Animal.yOffset` (documented for monkeys in crowns) and raw
  `setMotion`; `StrikeRunner`'s shapes are 2-D, so the swoop's height test rides `eligibility.maxDy` and
  `canReach`. Wanted: an altitude / 3-D strike shape for flyers (a `flight` block next to `steer`).
- **A custom weapon's viewmodel doesn't draw by itself.** The camera is not in the scene unless a kit weapon family
  adds it (`if (!cam.parent) scene.add(cam)` in Crossbow / Rifle / Bow), and the viewmodel pass (a depth clear at
  renderOrder 999, the model at 1000) is copied per family. The template's `camera.add(whip.model)` only shows because
  its iron sword adds the camera. Signal Dunes adds the camera from `buildEquipment` and copies the clearer into
  `weapons/whipModel.ts`. Wanted: a `blocks.viewmodel` verb that mounts a model in the viewmodel pass.
- **A backdrop's `clouds` dome is not added to the scene.** `Sky` keeps it on the camera but only the engine's own
  cloud layer is `scene.add`ed; ENGINE.md §13.1 doesn't say the backdrop must add it. Signal Dunes adds it itself.
- **The template's custom input context is the cause of the E365 audit's whip findings.** `template.whip` declares
  `attack` / `heavy` / `lock` with no `keys` (the `weapon.melee` defaults don't carry over), and its heavy reads
  `altHeld` while the touch melee hold sets `adsHeld`. Fixed here inside the shard: `sunscar.whip` declares
  `keys: { attack: ['Mouse0', 'KeyF'], heavy: ['Mouse2'] }`, binds `heavy` to the double crack, and a lifted touch
  hold (`adsHeld` true → false) throws it; `charge` fills the disc's ring. Wanted: the template (and SHARDS §5 step 4)
  show the keys and the `heavy` binding, or a custom melee context inherits `weapon.melee`'s keys.
- **The engine's far ridges and boundary are always built.** `Horizon` / `Boundary` come with every shard; a dune sea
  can only recolour them (the backdrop's `far.uHazeCol`), not drop or reshape them.

## API gaps (round 2)

Round 2 rebuilt the shard from `docs/SHARDS.md`, `src/shards/_template/` and `docs/ENGINE.md` alone (Z3R brief). Zero
engine edits; `pnpm gen --shard=sunscar-dunes` wrote only this slug's `shard-words` entry. The gaps are all
documentation: each one cost a read of engine source to get past.

- **A custom rig must have `body` and `head` bones.** The first served boot failed at `level.play` with
  `animal 'duneRay': rig has no bone 'head'` (`Animal` looks both up). ENGINE §16 / §19 and SHARDS §6 don't say so;
  the template's blob happens to have both. Wanted: the required bone names listed under `SpeciesLook`, or `head`
  optional for a custom rig.
- **`BoneDef.pos` is bind-space (absolute), and an animal's forward is +Z.** Neither is in §19; found by reading
  `AnimalFactory` and the template's `atan2(dx, dz)` steer. The first ray faced backwards. Wanted: one line each under
  `SpeciesLook.build()`.
- **Board captures need undocumented harness plumbing.** `window.__wildshard.pose()` throws unless
  `__wildshardHarness` was installed before load (parity's init script); `manifest.dev.poses` is only "capture
  poses" in §6 (its `eye` is an absolute world point, `feet` optional), and `scripts/parity/poses.mjs` has a
  hand-kept per-shard table, so a new shard's parity run captures no poses and its budget fields read `null`.
  Wanted: SHARDS §16's "portrait captures" step to name the capture tool, and parity to read `manifest.dev.poses`.
- **`TerrainPainter.build` gets no scope.** A painter's shader patch (`patchShader` wants `{ scope }`) and who
  disposes `terrain.mesh` / `terrain.material` are not documented. Signal Dunes patches the sand material in
  `compose` (which has the scope) and owns the material and geometry there. Wanted: `scope` in the painter's
  arguments and a line on ownership.
- **No "no ambience" value.** `manifest.audio.ambience` is required and the kit has only the forest bed; Signal Dunes
  keeps the template's `kit.ambience.forest` id but never calls `installForestAmbience`. Wanted: a documented silent
  ambience (or the field optional) until the generated wind bed lands.

## API gaps (round 3)

Round 3 rebuilt the shard again from `docs/SHARDS.md`, `src/shards/_template/` and `docs/ENGINE.md` (Z3R brief), on a
clean export of `f3a4a933`, then `961de2cf`. Zero engine edits; `pnpm gen --shard=sunscar-dunes` leaves
`lint/shard-words.generated.json` unchanged (same name and ids), so nothing under `lint/` is committed.

- **`audio.preload` could not be omitted (= G19, fixed mid-run by the lead in `92d1b752`).** At `f3a4a933` the served
  boot failed at `level.data`: `sunscar-dunes: boot audio requires the authored preload profile`, although ENGINE §15
  says an asset-free shard may omit `preload`. `961de2cf` carried the kit profile as a stopgap; `f65d8a48` drops it and
  boots on `NO_AUDIO` as the docs say. Nothing left to do.
- **`ThinkCtx` / `StrikeContext` fields are not documented.** ENGINE §19 names the types only. A flyer's brain needs to
  know that `ctx.player` is the player's *feet* (a sphere strike aimed there misses a chest-high swoop), whether
  `canReach` (occlusion + nav) works for a flyer or `ctx.reach(a)` (occlusion only) is the one to use, and what
  `StrikeContext.airborne` changes. Found by reading `src/engine/entities/species/registry.ts` and
  `src/engine/ai/strikes.ts`. Wanted: a field table for `ThinkCtx` and `StrikeContext` under §19 (the template's blob
  shows only `player`, `hurt`, `dt`, `calm`, `steer`).
- **`DamageRequest.stagger` / `knockback` have no type or unit in the docs.** §18 lists them by name; `tsc` says
  `stagger` is a number (seconds? a strength?). The heavy double crack was meant to stagger; it lands twice instead.
  Wanted: the type and unit of each optional `DamageRequest` field.
- Minor: §19 shows `SpeciesLook.build()` with no arguments; the type takes two. Only a test calls it (the contract
  test checks `rigContract.sockets` instead).

## API gaps (round 4)

Round 4 rebuilt the shard again from `docs/SHARDS.md`, `src/shards/_template/` and `docs/ENGINE.md` at HEAD (Z3R
brief), on a clean export of `e133c45d`. Zero engine edits. Every runtime need was covered by the docs (the creature
coordinates, bones, `ThinkCtx` / `StrikeContext` tables, the flyer example, `animal.stagger`, `ambience: 'none'`, no
`preload`, `keysFrom`, `equipmentHost.viewmodel`, the painter's scope, `horizon` / `boundary`, §6.1 board captures)
except one, a documentation gap:

- **Hiding the engine's sun disc after sunset (G-docs).** The dusk look wants the afterglow without a disc. §13.1 says
  the backdrop "gets `SkyBackdropTargets`" and §13.1's `SkyRig` note says `SkyBackdropView` owns "the clouds, disc,
  planet", but no doc lists the `SkyBackdropTargets` fields. The disc showed whenever the view turned toward the key
  light. Signal Dunes hides it in `bind(targets)` with `targets.disc.visible = false` and `targets.halo` (fields
  read off the exported `SkyBackdropTargets` type, a public `#engine` type export, not engine source internals).
  Wanted: a field table for `SkyBackdropTargets` in §13.1 (at least `disc` / `halo` and who may toggle them), or a
  `sky: { sun: false }` dressing switch next to `clouds` / `planet`.

Not a gap, for the next builder: any `grade.contrast` or split-tone on a very dark indigo zenith clips R and G to 0
and draws a hard band across the sky at ~30°; Signal Dunes runs a neutral grade.
