# E53

**Status:** done (2026-09-23, HUD build agent)
**Ask:** the title screen's NEW BUILD · TAP TO UPDATE pill doesn't respond to taps anymore on iPhone (Jake suspects the new full-height LOOK touch pad sits on top of it)


**Cause (found 2026-09-23, HUD build agent):** nothing covers the pill — on the title `#hud` carries `.intro`, so the touch
layer is `display: none`, and the pill is the hit-test winner at its centre (checked on the live build and on E46). The
pill read "NEW BUILD · TAP TO UPDATE", i.e. a waiting service worker had been announced; the tap handler then only called
`adopt()` (SKIP_WAITING → wait up to 2.5 s for controllerchange) and did nothing at all when the hand-over never landed —
e.g. the announced worker went redundant because a later deploy superseded it (deploys land every few minutes).
Reproduced on the live build in Chrome with a dead waiting worker stubbed: tap → nothing, still on the same page 4.5 s later.
**Fix:** `src/ui/Update.ts` — the tap shows "updating…" at once, adopts a waiting worker only if it isn't redundant, and
if the hand-over doesn't reload the page it falls back to the `?v=` cache-busting reload; it answers `pointerup` as well
as `click` (iOS drops a jittery tap's synthesized click; index.html cancels touchmove). Same stub on the fix: "updating…",
then reloaded with `?v=`. iOS 26.5 Safari simulator, real XCUITest tap on the pill: reloaded (`?v=` in the URL).
E46's touch-event cancelling lives on the touch layer only, which is hidden on the title, so it can't eat the pill's tap.

**Evidence:** commit `9287cef` — live build `9287cef-mueegpmm` (CI deploy run 35898409538 green).
