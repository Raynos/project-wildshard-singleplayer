# E144

**Status:** done (2026-09-25) — `c1f04a67`, live `c1f04a6-mugyvnrq` (sw.js strict install + the boot safety net verified on the live bundle)
**Ask:** (home-screen app) Hit TAP TO UPDATE and it got stuck: the loader sat at 00:00.0, DOWNLOAD 0 %, SETUP 0 %, build pill BD48540 · RELOAD. It didn't do anything; no error screen. A weird bug.


**Cause (2026-09-25, E144 subagent), reproduced in WebKit:** the service worker installed a build the host could no longer
serve. Vercel serves one deploy at a time: every other deploy's `/assets/*` answers 404 (checked: bd48540's `index-DtBEDqKw.js`
and `main-DzXZIEw2.js` are 404 on production now). bd48540 was live for ~2 min (11:58–12:00 UTC); deploys were landing every
~2 min. Its worker's install ran across that edge. `src/pwa/sw.js` precached the bundle **tolerantly**
(`cache.add(u).catch(() => undefined)`), so a code file that 404'd (the host was already on c95e298) was skipped. The worker
still reported *installed* holding bd48540's `index.html` + index chunk but no `main` / `three` chunk. The pill lit ("new build ·
tap to update"), the tap adopted that worker, and the reload ran bd48540's index chunk (hence the pill "BD48540 · RELOAD").
`src/boot/entry.ts` then did `import(main)` → 404 → "TypeError: Importing a module script failed". The error modal is armed
inside main.ts, so nothing caught it: a frozen loader at 00:00.0, TIER blank, 0 % / 0 %. A second path leads to the same
place: the document's background revalidate stored *any* live index.html in the worker's shell, including another build's,
whose chunks the worker never held.

**Repro:** three real `vite build`s served in turn on one origin by a Vercel-like host (only the live build's files, the
vercel.json headers), Playwright WebKit with the real service worker. Worker B installs while the host flips to C
mid-install, then the pill is tapped (or the app relaunched). Before the fix: the loader froze at 00:00.0 for 30 s+, with
`Importing a module script failed` and no modal, in both the tap case and the relaunch case. That is the user's screenshot.

**Fix:**
- `src/pwa/sw.js` install is strict. index.html is fetched no-store and must name only this build's code, and every
  JS / CSS file of the bundle must be fetched. Otherwise the install fails: the old worker keeps serving and the next
  `update()` retries with the live sw.js.
- The document revalidate and the `?v=` reload store a network index.html only when it is the worker's own build. Another
  build's is served but not kept, and it nudges `registration.update()`.
- `vite/pwa-plugin.ts` takes the bundle list after vite emits the stylesheet (`generateBundle` `order: 'post'`). Before, the
  worker never precached `style-*.css` and every activation pruned it: an offline launch after an update had no styles.
- Safety net: the new `src/boot/stuck.ts` watches entry.ts's `import(main)`.
  - **If the import fails:** it reports the error (`boot-entry`, queued when offline) and recovers by itself, once. It
    probes the host, adopts a waiting worker, drops the controlling worker's shell if its document names code no longer
    cached, and does a `?v=` reload (network-first).
  - **A second failure inside the budget:** a card with RELOAD. The budget is `src/core/reloadGuard.ts`, the error
    modal's guard moved into a shared module: 2 reloads in 2 min, then it only asks. It never loops.
  - **No connection:** the card says so and touches nothing.
  - **25 s without main:** a "Still starting" card with RELOAD, which goes away if main arrives.

**After, same harness:**
- race-then-tap: the bad install is refused and the tap boots the live build.
- race-then-relaunch: boots.
- adopt / revalidate: boot.
- main missing from the cache + host moved on: auto-recovers to the live build in ~1 s.
- The same with the host offline: the "No connection" card, then RELOAD after reconnecting boots.
- A 32 s main: the card at 25 s, gone at 36 s with main running.
- Before / after: `progress/253-e144-stuck-loader-before-after.jpg`.

**For the user's phone now:** a worker installed by the old code may still be incomplete. The next deploy's worker (with this
fix) replaces it. The first reload of a build that has the net recovers by itself.
