# E188

**Status:** done (2026-09-25) — `900800c8`, live as `900800c-muhwtpiv` (live sw.js carries fetchWhole; WebKit boots it clean).
**Ask:** Pressing RELOAD (the build pill) brings the loading page back and it just sits at 0% (00:00.0, tier blank, download — / setup —), build a5bf37b.


## What it was

**A download dropping mid-file, and nothing retrying it.** Not a deploy race — E185 said so and was wrong (see its
correction): Jake's failures landed while their own builds were stably live.

- WebKit reports a module whose body is cut off as exactly **"TypeError: Importing a module script failed."**, no
  stack — reproduced by resetting the socket halfway through the ~1.1 MB-gz `main` chunk. On LTE a hand-over does it.
- `src/boot/entry.ts` imported `three` and `main` once. One failure → the stuck card.
- Under the service worker, `cacheFirst` streamed the network response through as soon as its **headers** said 200,
  so a body that broke afterwards reached the page as a failed import, with no retry. It is also the path the pill's
  `?v=` reload takes when the new worker has not finished installing: the new build under the old worker, all from the
  network.
- The card's RELOAD met the same radio, so "reload didn't fix it".

## The fix

- **`src/boot/entry.ts`** — `retried()`: each boot import is tried twice more, 0.8 s and 2.5 s apart. WebKit fetches a
  failed module URL again on the next `import()` (tested; Chromium does not). A module that downloaded fine but threw
  is not run twice: the engine keeps it errored.
- **`src/pwa/sw.js`** — `fetchWhole()` for hashed JS / CSS: the worker reads the file **whole** before the page gets a
  byte, so a broken body becomes a throw it can retry (twice, 0.7 s and 2 s later, `cache: 'reload'` so an HTTP-cached
  failure is never replayed — the host sends `/assets/*` as `immutable` on every response, 404s included). Only a whole
  body is stored. Other assets stream as before.

## Follow-up (2026-09-26, Jake's pick: fix it at the host)

`vercel.json`: hashed code — `/assets/<name>.js|css` — is now `public, max-age=0, must-revalidate` instead of a year
`immutable`. Vercel puts the path's header on **every** response, 404s included, so a moment when a code file was
missing (Chromium tested: it keeps the 404 and never asks again) bricked that file on that device for a year. Now a
missing file is asked for again next time. The cost is one 304 revalidation per code file on a load that is not
worker-controlled; worker-controlled loads serve code from Cache Storage and never ask. Textures / models / other
hashed assets keep their long caching.
