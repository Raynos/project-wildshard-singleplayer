# E185

**Status:** done (2026-09-25) — not a code bug: a deploy race. No change made.
**Ask:** Boot error on the live build: TypeError: Importing a module script failed (build bcf12c4-muhuqijs, iOS Safari, /?chunk=driftwood-isle&explore=hub)


## What it was

A **deploy landing under a page that was already loading**, not a fault in the build.

- Jake's report: build `bcf12c4-muhuqijs`, **04:00:14.302Z**.
- `version.json` on production: build `8dcf03d-muhv2zko`, **04:00:17.373Z** — a new deployment went live
  **three seconds later**.

Vercel's production alias serves exactly one deployment's static files. His page had the previous deployment's
`index.html`, whose `<script type="module">` names hash-stamped chunks; the moment the alias flipped, those hashes were
no longer served from it and the import 404'd — "TypeError: Importing a module script failed", with no stack because
the failure is in the module loader, not in our code. `src/boot/stuck.ts` caught it and offered RELOAD, which is the
cure; the card he saw ("It broke again right after a reload") is the second-failure branch, i.e. the alias flipped
again during his retry. We were pushing several times a minute at the time (E162, E175, E176/E177 and two other
agents' commits), which is why it caught him twice.

Checked: the deployment live now serves its own entry chunk (200) and boots clean headless on an iPhone viewport.

**Nothing to fix in the code.** If it becomes a nuisance during a playtest, the lever is deploy cadence, not the app:
hold pushes while Jake is playing. Worth its own ask if he wants that enforced.
