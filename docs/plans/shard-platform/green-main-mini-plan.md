2. **"Perma" is overlap.** About 76 separate breaks landed in 72 h, about **1 an hour, or 1 commit in 24** (1,832

## Concurrency: the answer for Jake

- **GitHub already runs push CI your way:** one run at a time, never cancelled by a push. The newest push waits, and
  an older waiting push is dropped when a newer one arrives. GitHub labels the dropped run "cancelled" though it ran
  nothing (~1,000 of the 1,047 "cancelled" in 72 h).
- **But 46 running runs were killed in 72 h, all by hand.** sp-x7 ran `gh run cancel` (shown as "canceled by
  @Raynos") under a self-made "standing rule": cancel a superseded run so the fix starts sooner. 22 of those runs
  had no failure yet, and 24 hid their red results. Nothing else cancels a running run: the push loop doesn't, the
  deploy pin doesn't, and SW9 deleted CI's peer cancellation. The one exception is a job hitting its timeout
  (generated-inputs once, 10-24).
- **GM1 ends the manual cancels**, so every slow check finishes and the next run tests only the newest commits.

  refusals. A commit that touches shared SDK, engine, bake or build code also runs `tsc -b` and builds the products
  it touches. → **GM3**
- **G753:** the push gate runs the CI subset the outgoing commits touch (related tests, types, touched shard
  products) on the clean committed tree, with no budget skips (`scripts/push-loop.py:136`'s "DEFERRED TO CI" pass
  goes). While main is red, only fix commits push (G689). → **GM2**
- **G754:** the lane whose commit broke main stops and fixes it at once. sp-x7 names the culprit commit and lane, and
  takes over any red older than 30 min. → **GM6**
- **G756:** hard wall caps: **pre-commit ≤ 60 s, push gate ≤ 180 s per batch.** The "clean tree" is the one existing
  build mirror the push gate already uses, updated incrementally, never a new checkout, export or per-lane copy.
  Outgoing batches go through one push queue. Checks are selected and made faster to fit the caps, never cut (G703).
  Timeouts stay, and no deferral is ever silent (G752). What a push-gate step does at its cap is Q1.

## Questions for Jake

- **Q1 When a push-gate step hits 180 s, what happens?** Options: (1) Skip for now. (2) Refuse the batch and name the
  slow step: nothing pushes until someone makes it faster. One slow commit then blocks every lane behind it on a
  shared `main`. (3) **Hand only that step to CI, tagged.** The rest of the batch's checks must pass. The push log
  and a `Gate-deferred: <step>` line in the push record name the step and the batch's commits, so a red is pinned
  at once. CI's run runs that step first, and the overrun becomes a GM4/GM2 speed row the same hour. (4) Split the
  batch: push the longest prefix whose checks fit, and retry the rest next tick. That doesn't help when a single
  commit's step is over the cap. **Recommended: (3), with (4) first when the batch has more than one commit.** It is
  never silent, it never blocks the queue, and the culprit is known in advance.
- **Q2 Quarantine slow or flaky tests instead of blocking?** Options: (1) Skip for now. (2) **Yes: a test that turns
  main red twice in 24 h with no code cause moves to a non-blocking quarantine job.** It still runs and reports,
  gets an owner and a 24 h fix, and returns to blocking when fixed. Nothing is deleted and no assertion is loosened
  (G690 stays). (3) No: every test blocks until it's fixed, as today. **Recommended: (2).** Nalati product tests
  alone opened 9 windows.
- **Q3 Merge queue, or push-then-test plus a faster first verdict?** Options: (1) Skip for now. (2) **Push-then-test
  as today, with GM2's red hold, plus a `related-first` CI job.** That job runs the tests related to the files
  changed since the last green SHA right after checkout, for a first verdict in under 8 min, at the cost of more CI
  minutes (G691 accepted that). (3) Merge queue: push to a candidate ref, and main fast-forwards to the newest green
  candidate. Main stays green by construction, but on one shared tree a red candidate blocks every lane exactly as
  red main does today, and a CI job has to move main. **Recommended: (2).** GM2 already stops the overlap a queue
  would hide.
