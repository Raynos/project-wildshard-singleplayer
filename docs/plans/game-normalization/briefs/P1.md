# E357 job P1 — make the parity harness fast (wall clock)

Read `docs/plans/game-normalization/brief-common.md` first: its rules bind you, except: this job is the harness, so run
it in the browser as often as you need (always through `scripts/browser-lane.sh`, `--mute-audio`; the lane allows 8).

## Why
Jake (2026-10-01): a full parity record takes 25–70 minutes (4 shards × phone / desktop × 3 runs, serial), the narrow
checks 4–15 minutes; that wall clock is the build's biggest drag. Make it a lot faster without making it weaker: the
same fields compared, the same determinism.

## The job (measure first: time each phase of one shard × tier today and write the table in your handoff)
1. **Parallel inside the harness.** `--jobs=N` (default: the free browser lanes, max 8): every shard × tier, and a
   record's 3 runs, in parallel browsers from **one** export + build per SHA (today each process exports and builds
   its own). Lane slots per browser, so the machine-wide lane still caps everything.
2. **Reuse builds.** Cache the export build by the SHA's tree hash (e.g. `~/.cache/wildshard-parity/<tree>/dist`), so
   a second run on a SHA (or a SHA whose runtime tree is unchanged) skips export + install + build.
3. **Compress time.** The harness drives the game on a fixed capture clock (capture = 30). Make every scripted wait a
   **frame / game-time** wait, never a wall-clock `waitForTimeout`, and let frames render as fast as the GPU allows (no
   rAF throttling, no real-time sleeps). The walk, combat, pause and leak then run faster than real time on the M5 with
   the same game-time trajectory, so the fields stay identical. Prove it: the same SHA recorded at the old speed and the
   new must compare green (every field, 3 runs each).
4. **A fast profile.** `--fast`: one run, phone tier only, the gate fields (boot fingerprint, walk stuck / out, combat
   hits / kills, pause → resume, leak), poses at the reduced set the gate needs. Target ≤ 10 minutes for all four
   shards on the M5. The full profile stays for milestones and records.
5. Anything else your measurement shows (boot waits, title fast path, asset warm-up, SW install).
- Keep 03-harness-gate's semantics; write each change into 03 (one-line edits citing P1) where the spec described the old
  behaviour.
- Done when: your handoff's before / after timing table shows the full record and the fast profile times, the

  slot API only), `test/parity*`, the parity sections of 03. Probe changes in `src/engine/debug/probe.ts` only if a
  wait needs a game-time hook (coordinate over herdr; others are live).
