# Round 1 — seat A

> **State:** independent review, 2026-10-01. Lens: open-world/MMO game direction and the S1–S8 battery. Code references are to `wildshard-singleplayer` at `pre-normalization` (`dcd6a29a`); no build was played.

The strongest argument is that a shard needs one owner designing the experience and the space together, with real phone play before expensive production. The inventories support that diagnosis. The weaker argument is that sufficient first-pass content already exists and adding a Living World grammar will make it fun for hours. Waiting, travel and unverified fights are being counted as content; slot counts and reward resets cannot establish enjoyment. A director needs to specify the player's decisions, the staging and consequence of those decisions, and a satisfying stopping point. Driftwood should make exploration and swordplay reveal an island mystery; Pine should make a deliberate hunt become an eerie encounter; Nalati should make riding and protecting the camp matter; Nine Dragon should make choosing and mastering vertical routes change access through a lived-in city. Those are different games within shared controls and legibility. The document offers useful ingredients, but not yet sufficient direction to build or review those experiences without substantial guessing.

## Battery

- **S1 — partial.** Pitch → beats → map/unlocks/sightlines → pacing artifacts are specified; workable gate order, first-fortnight scope and delegation are not (A1–A2). Greybox → first mockup has conflicting gate descriptions; use A2's illustrative sprint after SDK availability, not an implied two-week full-grammar delivery.
- **S2 — partial.** Start with a pitch/Beats review (§13), then the limited slice (§9), is answerable. Which built pieces survive → where to prototype envelope/lift/yank → when Jake authorizes further strata requires guessing (A3); repeatable-loop proof also comes too late (A1).
- **S3 — fail.** Arrival phase → available goal → hunt → local event → claim/payoff → bus-stop exit is not provided. Current clock/boss lengths do not guarantee completion, and the proposed loss closes the board (A4); actual portrait control feasibility is still untested (A11).
- **S4 — partial.** Centre/router → today's shard → event/adventure → currency/cosmetic progress is a plausible framework. A finished player's particular goal, changed decisions, earning budget and satisfying capped session are undefined (A5); assignment availability is undefined (A6).
- **S5 — partial.** Scaffolding → slots → static check → played check is described. Required versus recommended floors → ritual/publication → first discovery → reachable routed objective needs A6; phase/death/reload/failure coverage needs A7. Slot counts alone do not certify a playable upload.
- **S6 — partial.** Existing quest and optional collectibles supply a candidate hour, but §9 supplies an event menu rather than a staged route. Arrival → lookout → wreck/cave → shrine → post-finale loop cannot be checked against the density intervals without A8; edge entries, the 200/280 m legs and traversal variants are audit targets, not measured dead-time findings.
- **S7 — partial.** Shared clock → event/boss participant scaling is specified. Cooperative jobs → shared outcome → personal credit → late join/death/leave → reward/reset behaviour is not (A9); the meta's actual principal climax also needs a decision in the shard design.
